WebForge 容器化实战(上):Docker 配置与网络排查

约 2511 字大约 8 分钟

2026-10-29

本文整理自 2025-09-05 用 Claude Code 调试「WebForge」项目容器化的一次完整会话记录。WebForge 是一个基于 FastAPI + Uvicorn + Playwright 的网页转文档服务(Python 3.11),目标是把它用 Docker Compose 部署起来。这一篇聚焦配置类问题:环境变量不生效、端口不一致、时区错误、宿主机访问不通,以及容器之间如何互相访问(MinIO)。镜像构建与 Playwright 浏览器踩坑见下篇。

读者可以学到:

  • Docker 容器中环境变量、端口、时区的正确配置方式,以及"改配置"与"改镜像"的取舍;
  • 容器内 127.0.0.1 与宿主机 127.0.0.1 的本质区别,和两种跨容器访问方案;
  • 与 AI 编码助手协作排查问题时"现象 → 提问 → 定位 → 验证"的节奏。

问题一:local 环境启动,日志却显示 prod

现象

用 docker compose --profile local up webforge-local 启动(对应 .env.local),启动日志却显示:

app_version='v0.0.7' app_env='prod' app_name='WebForge' app_host='127.0.0.1' app_port=9080 ...
  运行环境:  prod

但我明明是用 webforge-local(加载 .env.local,其中 APP_ENV=local)启动的。

Claude Code 的排查过程

它按"配置文件 → 代码读取逻辑 → Dockerfile"的顺序逐层定位,这也是排查环境变量问题的一般路径:

⏺ Read(.env.local)
  ⎿  Read 33 lines (ctrl+r to expand)

⏺ 奇怪，.env.local 文件中 APP_ENV=local 是正确的，但日志显示的是 prod。让我检查一下应用代码如何读取环境变量：

⏺ Search(pattern: "运行环境", output_mode: "content")
  ⎿  Found 4 lines (ctrl+r to expand)

⏺ Read(app/config/__init__.py)
  ⎿  Read 66 lines (ctrl+r to expand)

⏺ 现在我明白问题了！问题在 Dockerfile 中。让我检查 Dockerfile：

⏺ Read(Dockerfile)
  ⎿  Read 50 lines (ctrl+r to expand)

⏺ 找到问题了！Dockerfile 的 CMD 命令硬编码了 --env=prod，这覆盖了环境变量文件的设置。
# ...(省略)

根因与修复

Dockerfile 的 CMD 硬编码了 --env=prod,命令行参数的优先级高于环境变量文件:

  # Run the application
- CMD ["python3", "main.py", "--env=prod"]
+ CMD ["python3", "main.py"]

修改 Dockerfile 后需要重新构建镜像才能生效,重启容器是不够的:

docker compose --profile local down
docker compose --profile local build webforge-local
docker compose --profile local up webforge-local

重新构建后日志正确显示 运行环境: local、app_env='local'。

小结

  • 容器镜像一旦构建,里面的文件(包括 CMD)就固定了,改镜像内的东西必须重新 build;
  • 运行环境这类"会随部署变化的量"应该交给环境变量/配置文件,不要烧死在镜像里。

问题二:端口映射与配置文件不一致

第一轮:让 Docker 跟随各环境的端口

我选中 docker-compose.yml 里的端口映射提问:容器内的端口为什么是 8000?没有覆盖配置文件中的配置,应该和配置文件保持一致吧?

Claude Code 检查后发现各环境配置的端口并不相同:.env 与 .env.local 是 9080,.env.prod 是 9026。于是第一轮把 docker-compose.yml 三个服务的端口映射、健康检查,以及 Dockerfile 的 EXPOSE/HEALTHCHECK 都逐一改成与各环境配置一致(9080/9080、9026/9026)。

更优解:统一端口为 8000,免去重新打包

我随即提出:改了 Dockerfile 就得重新打包镜像,不如反过来把配置文件的端口统一改成 8000,复用现有镜像。Claude Code 认可这个思路,做了反向调整——三个 env 文件全部 APP_PORT=8000,docker-compose 与 Dockerfile 全部回到 8000:

# docker-compose.yml(每个服务)
ports:
  - "8000:8000"
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
# Dockerfile
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=30s --start-period=5s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

这样处理的好处:

  • 不需要重新构建镜像——env 文件和 compose 的 environment 是运行时注入的,重启容器即生效;
  • 配置统一——所有环境同一个端口,管理简单;
  • 即时生效——后续调整只需改配置文件。

经验:容器化的项目,建议"容器内端口全局统一 + 靠映射/配置适配环境",而不是每个环境一套容器内端口。

问题三:容器日志时区不对

先硬编码 TZ

现象是日志时间与系统时间对不上。先确认宿主机时区(date 显示 CST,/etc/localtime 指向 Asia/Shanghai),第一版方案是在 docker-compose.yml 中给每个服务加:

environment:
  - TZ=Asia/Shanghai

更通用的方案:挂载宿主机时区文件

硬编码的问题在于换一台服务器就又错了。改用 volume 挂载宿主机的时区文件,让容器自动跟随宿主机:

volumes:
  - /etc/localtime:/etc/localtime:ro   # 挂载宿主机本地时间
  - /etc/timezone:/etc/timezone:ro     # 挂载宿主机时区配置

同时删掉 TZ=Asia/Shanghai 环境变量。验证:

$ docker exec webforge-app-local date
Fri Sep  5 15:43:01 CST 2025          # 容器时间

$ date
2025年 9月 5日 星期五 15时43分07秒 CST  # 宿主机时间,一致

这个方案的优势:

  1. 自动同步:容器时区与宿主机保持一致;
  2. 便携性:部署到任何地区的服务器都会用当地时区;
  3. 免维护:不需要手动改配置;
  4. 只读挂载(:ro):容器不会反向修改宿主机的时区文件。

问题四:宿主机访问不到 localhost:8000

容器启动正常,但本机连 http://localhost:8000/health 都打不开。排查时发现 slim 基础镜像里连 netstat/ss 都没有:

⏺ Bash(docker exec webforge-app-local netstat -tlnp)
  ⎿ Error: ... exec: "netstat": executable file not found in $PATH
# ...(省略)

最终从应用启动日志里看到关键信息:应用绑定的是 127.0.0.1:8000。根因是 .env.local 中 APP_HOST=127.0.0.1——在容器里这只监听容器自己的 loopback,宿主机的请求经端口映射进来后到不了应用。

  # .env.local
- APP_HOST=127.0.0.1
+ APP_HOST=0.0.0.0

改成 0.0.0.0 监听所有网卡后,curl http://localhost:8000/health 已经能连上(此时返回的是业务层的"接口路由不存在",但网络链路已经通了,这是两个不同层面的问题)。

经验:容器内的服务要对外提供访问,监听地址必须是 0.0.0.0;127.0.0.1 只在"容器访问自己"时有意义。

问题五:容器内访问 MinIO 被拒连

接口报 500:

{
  "code": 500,
  "msg": "MinIO保存文件失败: 保存文件到MinIO失败: HTTPConnectionPool(host='127.0.0.1', port=9000): Max retries exceeded with url: /matiaspress?location= (Caused by NewConnectionError('<urllib3.connection.HTTPConnection object ...>: Failed to establish a new connection: [Errno 111] Connection refused'))",
  "data": null
}

我的判断是:MinIO 也是用 Docker 部署的,映射到本机 9000 端口;WebForge 容器里配置的 127.0.0.1:9000 指向的是它自己容器内部,当然连不上。是否应该把两个项目放进同一个 Docker 网络?Claude Code 确认了判断,并给出两个方案:

  • 方案一:走宿主机地址。macOS/Windows 用 host.docker.internal,Linux 用 172.17.0.1(或 --add-host=host.docker.internal:host-gateway);
  • 方案二(推荐):加入 MinIO 所在的 Docker 网络,直接用容器名当域名。

落地:外部网络 + 容器名访问

先确认 MinIO 容器与它所在的网络:

$ docker ps | grep -i minio
69e2b8c3be4c   docker.1ms.run/minio/minio:latest   ...   0.0.0.0:9000-9001->9000-9001/tcp   minio

修改 docker-compose.yml,让 webforge-local 同时加入默认网络和 MinIO 的外部网络:

# 服务下
    networks:
      - default
      - minio-network

# 文件顶层
networks:
  minio-network:
    external: true
    name: minioimagor_minio-imagor-network

再把 .env.local 的 MinIO 地址从本机映射端口改为容器名:

  # .env.local
- MINIO_ENDPOINT=127.0.0.1:9000
+ MINIO_ENDPOINT=minio:9000

验证方式

slim 镜像里没有 nslookup/ping,没法直接测连通性,改用业务验证:写一个 MinIO 连接测试脚本,docker cp 进容器执行,连接成功;再走一遍转换接口,文件正常上传 MinIO。

经验:

  • 容器之间互访,优先"同一个 network + 容器名",比记宿主机 IP/端口映射更稳;
  • external: true 用于引用不在本 compose 文件里定义的已有网络(比如另一个 compose 项目创建的网络);
  • 精简镜像缺调试工具时,可以直接用业务接口或临时脚本验证连通性。

顺带修复:Playwright 异常类引用错误

网络打通后接口仍报 500,日志里暴露的其实是另一个问题——代码里引用了不存在的异常类写法。Playwright 的 Error 类并没有 TimeoutError 子类:

  # 导入
- from playwright.async_api import Error as PlaywrightError
+ from playwright.async_api import Error as PlaywrightError, TimeoutError as PlaywrightTimeoutError

  # 异常处理
- except PlaywrightError.TimeoutError as to_ex:
+ except PlaywrightTimeoutError as to_ex:
      logger.error(f"截图超时: {str(to_ex)}")
      screenshot_error = str(to_ex)
- except PlaywrightError.Error as pw_ex:
+ except PlaywrightError as pw_ex:
      logger.error(f"Playwright 截图错误: {str(pw_ex)}")
      screenshot_error = str(pw_ex)

注意:代码是构建时 COPY 进镜像的,改完代码要重新 build 镜像才会生效,单纯 restart 容器没有用。

流程沉淀:每轮修复后的版本记录与提交

这次实战中每解决一类问题,都会让 Claude Code 更新 VERSION.md 并提交一次 git commit,commit message 用中文描述变更,例如:

git add .
git commit -m "fix: 优化Docker配置并统一端口管理"   # 端口统一
git commit -m "feat: 优化Docker时区和网络配置"      # 时区挂载 + 0.0.0.0

对应版本节点:v0.0.8(Docker 容器化支持)→ v0.0.9(时区与网络配置优化)→ v0.0.12(容器化问题集中修复)。

本篇小结

  1. 镜像里的东西改了要重新 build(CMD、代码、依赖),配置类的东西(env、compose 的 environment/volumes)重启即可;
  2. 运行环境、端口等易变配置交给环境变量,不硬编码进镜像;
  3. 容器内服务监听 0.0.0.0,否则宿主机映射了端口也访问不到;
  4. 时区用挂载 /etc/localtime、/etc/timezone(只读)跟随宿主机,不要写死;
  5. 容器互访用同一 Docker 网络 + 容器名,127.0.0.1 在容器里指的是容器自己。
